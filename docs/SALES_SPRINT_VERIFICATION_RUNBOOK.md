# Runbook проверки на 14-дневный коммерческий спринт

Цель: **повторяемые шаги** для деплоя и smoke-тестов без добавления функций.  
Чеклист env и плейсхолдеров: `SALES_SPRINT_LIVE_CHECKLIST.md`.  
Автоматизированная проверка: `LAUNCH_VERIFY_RUNBOOK.md` (`npm run verify:launch`).  
**Петля VK (архитектура и роли):** `VK_SALES_LOOP_V1.md`.

## 1. Порядок команд (эталон)

Выполнять после настройки `.env` по чеклисту.

| Шаг | Каталог | Команда |
|-----|---------|---------|
| 1 | `project/CRM/crm-mvp/backend` | `npm install` |
| 2 | там же | `npx prisma migrate deploy` |
| 3 | там же | `npx prisma generate` |
| 4 | там же | при необходимости `npm run db:seed` |
| 5 | там же | `npm run start` (сервер на `PORT`, по умолчанию 4000) |
| 6 | `project/CRM/crm-mvp` | `npm run verify:launch` (API по умолчанию `http://localhost:4000/api`) |
| 7 | `project/CRM/crm-mvp/frontend` | `npm install` → `npm run build` |

Опционально полный smoke с заказом:

```bash
cd project/CRM/crm-mvp
npm run verify:launch:full
```

Другой хост:

```bash
npm run verify:launch -- --api-base https://ВАШ_ХОСТ/api
```

## 2. Health checks

| Проверка | Как | PASS |
|----------|-----|------|
| Бэкенд жив | `GET {API_BASE}/../health` если API_BASE заканчивается на `/api`, то **база без /api**: например `http://localhost:4000/health` | JSON `ok: true`, `data.status === "healthy"`, `dbConnected: true` |
| Публичные филиалы | `GET …/api/public/branches` | `ok: true`, массив не пустой (после seed) |
| CRM авторизация | `GET …/api/dashboard/launch-kpis?branchId=ID&days=1` с заголовком `X-CRM-Token: <токен>` | `ok: true`, не 401 |

> Если `API_BASE` в переменных verify = `http://localhost:4000/api`, health обычно на `http://localhost:4000/health` (без `/api`).

## 3. Ручные smoke-сценарии

Предусловия: меню на **завтра** для филиала Чебаркула (или выбранного) заполнено в CRM; лендинг указывает на тот же API.

### 3.1 Публичный B2C-заказ — PASS

1. Открыть лендинг с верным API (`?api=…` или storage).
2. Убедиться, что статус меню **«Можно оформить заказ»** / live.
3. Выбрать позиции, заполнить имя/телефон, отправить.
4. **PASS**: ответ успеха, id заказа; в CRM заказ виден на дату доставки «завтра».

**Частые сбои**: меню не live; 429 rate limit; неверный `Content-Type`; заполнен honeypot.

### 3.2 VK — прямой структурированный заказ — PASS / FAIL

**Предусловия:** в `.env` заданы `VK_*`, webhook в VK указывает на ваш `POST /api/vk/webhook`; для точки по умолчанию заполнено **меню на завтра**; бот отвечает в диалоге.

**Шаги:**

1. В открытом диалоге с сообществом пройти сценарий **заказа из бота** (филиал → позиции → ФИО/телефон/адрес) до подтверждения, как в `VK_DIRECT_ORDER_CAPTURE_V1.md`.
2. Открыть CRM → **«Заказы и KPI»**, выбрать ту же точку и **дату доставки = завтра** (как в боте).
3. Включить фильтр **«Только VK»** или **«VK · новые»** — заказ должен быть в списке.
4. Открыть карточку: канал **VK**, текст **«Заказ из VK-бота (прямой сценарий)»**, при наличии — строка **VK:** с `vk_direct_v1` и peer/user.

**PASS:** заказ создан в БД, виден в списке, статус меняется с карточки.  
**FAIL:** бот не отвечает; заказ не появился (проверить меню, филиал, логи сервера); в CRM 401 (токен).

**Частые сбои:** пустой `VK_GROUP_ACCESS_TOKEN`; неверный `VK_WEBHOOK_SECRET`; Callback URL не тот; меню на дату пустое; блокеры на экране **«Лиды VK»** (готовность).

### 3.2b VK — fallback-лид — PASS / FAIL

**Шаги:**

1. В боте довести сценарий до **«оставить заявку»** / лид-формы (или сценарий, где заказ не оформляется, см. `VK_OPERATOR_ORDER_FLOW.md`).
2. CRM → **«Лиды VK»**.
3. Нажать **«Обновить»**; при необходимости фильтр **«Только NEW»** или **«Нужен ответ»**.
4. Открыть лид: видны **peer / user**, статус; блок **«VK сейчас (сводка)»** показывает ненулевые счётчики при наличии данных.
5. **«Создать заказ в CRM»** → сохранить заказ с позициями.

**PASS:** лид в таблице; после создания заказа у лида связь/статус согласно логике; в списке заказов виден заказ с **связью с лидом VK** (если применимо к вашему сценарию конвертации).  
**FAIL:** лид не создаётся; 401 на `/api/vk-leads`; пустая таблица при реальном сообщении — проверить webhook и БД.

### 3.2c Сводка и кросс-проверка даты

На экране **«Лиды VK»** счётчики заказов VK на дату берут **ту же точку и дату доставки**, что выбраны на экране **«Заказы»** (чтобы оператор не прыгал между контекстами). Смените дату на «Заказы» → вернитесь в «Лиды VK» → **Обновить** — цифры должны соответствовать.

### 3.3 Ручной заказ в CRM — PASS

1. Открыть CRM с `VITE_CRM_TOKEN` = серверному токену.
2. «Быстрый заказ» или экран заказов: создать заказ, сменить статус.
3. **PASS**: заказ в списке, статус меняется без 401/500.

### 3.4 B2B-форма на лендинге — PASS

1. Секция «Обед в офис», заполнить поля, отправить.
2. **PASS**: `POST /api/public/corporate-leads` возвращает `ok: true`; в CRM раздел B2B видна новая заявка.

**Частые сбои**: CORS если форма с другого origin; 429; валидация полей.

### 3.5 Конвертация лида в компанию — PASS

1. В CRM B2B: открыть лид без компании → «В компанию», выбрать филиал при необходимости.
2. **PASS**: появилась компания, у лида статус/привязка; повторная конвертация даёт конфликт (ожидаемо).

### 3.6 Повторный B2B-заказ — PASS

1. В карточке компании «Быстрый заказ», добавить позиции, сохранить.
2. **PASS**: `DeliveryOrder` создан, в ответе/карточке при необходимости виден `companyAccountId`.

## 4. Что считать PASS для спринта

- `npm run verify:launch` → **RESULT: PASS**
- Health + branches + KPI с токеном — OK
- Один успешный ручной B2C с реальным меню — OK
- CRM создаёт/патчит заказ — OK
- (Если VK в продаже) хотя бы один сквозной сценарий VK — OK
- B2B: заявка + конвертация + заказ с компанией — OK по мере использования B2B в спринте

## 5. Расшифровка типичных ошибок

| Код / симптом | Значение |
|---------------|----------|
| 401 на CRM API | Неверный или отсутствующий `X-CRM-Token` |
| CORS в консоли браузера | Origin не в `POLDEN_CORS_ORIGINS` / `PUBLIC_SITE_ORIGIN` / CRM origin |
| 429 | Rate limit публичных POST — подождать окно (см. `PUBLIC_ORDER_RATE_*`) |
| 415 | POST не `application/json` |
| SPAM_REJECTED | Заполнено поле `polden_hp` |
| Branch table empty | БД пустая — migrate + seed или `POLDEN_ALLOW_EMPTY_DB` только осознанно |
| Заказ на лендинге закрыт | Нет валидного меню на завтра в API для выбранного филиала |
