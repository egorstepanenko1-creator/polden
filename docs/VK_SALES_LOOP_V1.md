# VK sales loop v1 — аудит готовности к живым продажам

Документ описывает **фактическое** состояние кода (без MAX и новых каналов). Цель — закрыть петлю «трафик VK → конверсия → оператор в CRM».

---

## 1. Точки входа VK

| Точка | Где в коде | Назначение |
|-------|------------|------------|
| **Callback API** | `POST /api/vk/webhook` (`vkWebhookRoutes.js`) | Входящие события сообщества; секрет `VK_WEBHOOK_SECRET`, подтверждение `VK_CALLBACK_CONFIRMATION_CODE`. |
| **Бот / сценарии** | `vkBotHandler.js`, `vkOrderHandler.js` | Лид-форма, меню из CRM, **структурированный заказ** и откат в лид. |
| **Исходящие** | `vkSend.js` | `messages.send`, требуется `VK_GROUP_ACCESS_TOKEN`. |
| **Лендинг** | `landing-order/index.html`, блок `#contact-bridge` | Ссылка на сообщество и строка поддержки через **`POLDEN_LAUNCH_BRIDGE`** (заполняется вручную перед боем). |

Публичный сайт **не** является точкой входа VK-бота, но даёт мост «написать в VK».

---

## 2. Прямой заказ из VK (structured order)

**Путь:** пользователь проходит сценарий выбора филиала → корзина по слотам меню → контакты → `createDeliveryOrderFromInput` с `sourceChannel: 'VK'`.

- Меню: `MenuDayItem` на дату «завтра» (логика `vkOrderMenu.js`, `vkOrderDates.js`).
- Атрибуция JSON: `utm_source=vk`, `utm_medium=bot`, `order_capture=vk_direct_v1`, `vk_peer_id`, `vk_user_id` (`vkOrderHandler.buildVkOrderAttribution`).
- В CRM заказ: **`sourceChannel === 'VK'`**, **`vkLeadId` обычно null** (лид не создаётся при успешном прямом заказе).

**Оператор видит:** экран «Заказы», карточка с бейджем канала VK, строка «Заказ из VK-бота (прямой сценарий)», компактная строка **VK:** с `order_capture` / peer / user из атрибуции.

---

## 3. Fallback: лид VK

Если структурированный заказ невозможен или пользователь выбирает «оставить заявку» — создаётся **`VkLead`** (`vkBotHandler` и др.).

- Статусы: `NEW`, `CONTACTED`, `CONVERTED`, `REJECTED`.
- CRM: **`GET/POST/PATCH /api/vk-leads`**, карточка лида с `peerId`, `vkUserId`, сырой JSON.
- Конверсия в заказ: оператор **«Создать заказ в CRM»** → модалка с `vkLeadId` → при сохранении заказ получает **`vkLeadId`** и канал VK.

**Оператор видит:** раздел «Лиды VK», таблица + деталь, быстрые фильтры (все / NEW / нужен ответ), сводка **`GET /api/vk-leads/snapshot`**.

## 5. Env / конфиг для боя

См. `backend/.env.example`, `PUBLIC_ORDER_HARDENING.md`, `configStartup.js`.

Обязательно для прод-режима (production-like): **непустой** `CRM_INTERNAL_TOKEN`, **CORS origins**, **`VK_WEBHOOK_SECRET`**, заполненные **`VK_GROUP_ACCESS_TOKEN`**, **`VK_CALLBACK_CONFIRMATION_CODE`**, рабочий **`PUBLIC_SITE_ORIGIN`** для ссылок в CRM.

Опционально: **`VK_OPERATOR_CONTACT_TEXT`**.

## 6. Что остаётся за человеком

- URL сообщества и поддержка на лендинге (`POLDEN_LAUNCH_BRIDGE` + см. `landing-order/POLDEN_LAUNCH_BRIDGE.md`).
- Настройка Callback URL в кабинете VK на ваш хост `/api/vk/webhook`.
- Ежедневное **меню на завтра** для точки, с которой бот работает.
- Материал **MENU_DAILY** (контент-пайплайн) для текста меню в боте — по текущей логике `vkMenuContent.js`.

## 7. Что по-прежнему ручное

- Ответы клиенту в VK (бот отправляет шаблоны; сложные кейсы — оператор вне CRM или доработки вне этой задачи).
- Перевод лида в заказ — **явное действие оператора** («Создать заказ в CRM»).
- Смена статусов заказа и лида — оператор.

## 8. Технической «достаточности»

- Поток **прямой заказ VK → DeliveryOrder** уже реализован; не требует дублирующей логики.
- **Трассировка** peer/user в атрибуции уже писалась в БД; в v1 добавлено **лёгкое отображение** на карточке заказа.
- Тяжёлая аналитика не нужна: достаточно **snapshot** и фильтров на существующих списках.

## 9. Диагностика: текст «Заявка принята…» vs прямой заказ

- В коде **`MSG_LEAD_ACCEPTED`** (`messages/vkBotRu.js`) отправляется **только** из ветки `COLLECT_COMMENT` в `vkBotHandler.js` после `vkLead.create` — то есть только после **полного** сценария «Оставить заявку».
- Ранее кнопка **«Оформить заказ»** запускала `startVkStructuredOrder` **только** при `currentState === IDLE`. Если пользователь уже был в `COLLECT_*` (начал заявку), нажатие «Оформить заказ» обрабатывалось как ответ в форме лида и заканчивалось тем же **«Заявка принята…»** — это **ошибка приоритета в репозитории**, а не отдельный «старый бот».
- **Исправление:** при «Оформить заказ» из состояний сбора лида черновик заявки сбрасывается и вызывается `startVkStructuredOrder` (см. `vkBotHandler.js`, `isLeadCollectionState`).
- Если **`vkStructuredOrderReady=false`** в `GET /api/vk-bot/readiness`, при «Оформить заказ» бот честно пишет, что **меню на завтра пусто** (`MSG_ORDER_MENU_EMPTY`) и предлагает заявку — пользователь может дойти до **лида** без бага маршрутизации; проверяйте `MenuDayItem` и env.
